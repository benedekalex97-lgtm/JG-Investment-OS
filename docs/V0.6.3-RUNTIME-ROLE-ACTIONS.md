# JG Investment OS — Neon preview `jg_runtime` szerepkör GitHub Actionsből (v0.6.3)

## Állapot és hatókör

A workflow **még nem futott**, a `jg_runtime` szerepkör **még nem létezik**, a Neon adatbázis nem változott. Ez a PR csak a kézzel indítható workflow-t és a leírást tartalmazza.
A workflow csak `workflow_dispatch`-csel indul (nincs push/PR/schedule trigger), csak az alapértelmezett ágról, és kizárólag a `jg_os_preview` adatbázis `jg_runtime` szerepkörét kezeli.
Nincs ügyféladat-import, nincs production művelet, nincs Vercel-projektbeállítás (csak a repóbeli `vercel.json`, lásd lent). A merge és az indítás **külön felhasználói jóváhagyást** igényel.

## Mit csinál a szerepkör?

A futási (alkalmazás) kapcsolat jogosultságát választja le a séma-tulajdonosról. A tulajdonos (`jg_os_preview_owner`: CREATEROLE, CREATEDB, BYPASSRLS, `neon_superuser`) a migrációhoz és a felhasználókezeléshez marad; a Vercel Preview `DATABASE_URL` később a `jg_runtime`-ot használja.

| Tulajdonság | Érték |
|---|---|
| Attribútumok | `LOGIN`, `NOINHERIT`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOBYPASSRLS`, kapcsolatkorlát 20 |
| `jg_app` | `SET` igen (`SET LOCAL ROLE jg_app`), `INHERIT` nem, `ADMIN` nem: a CRM-adatot csak a `jg_app`-ra váltva, RLS-sel éri el |
| `users` | SELECT + UPDATE(`last_login_at`) (nincs jelszó-módosítás, létrehozás, törlés) |
| `sessions` | SELECT / INSERT / UPDATE / DELETE |
| `login_attempts` | SELECT / INSERT / DELETE |
| `meta`, `schema_migrations` | SELECT |
| CRM- és naplótáblák | közvetlen jog **nincs** |
| Séma | nincs CREATE a `public` sémán és az adatbázison; nem tulajdonos |
| Jelszó | SCRAM-SHA-256 verifierként kerül az adatbázisba; a tiszta jelszó nem jut el a szerverre, az utasításszövegbe és a naplókba |

A kódot (`src/server/db/runtime-role.ts`, `scripts/db.ts`) a v0.6.2 PR (#2) tartalmazza; a workflow egy **rögzített, átnézett commitot** futtat:
`bd407f13bf2967511e282b81bf7ba1481181dc18` (v0.6.2 ág). Ha a PR #2 squash-merge-elésre kerül vagy a SHA elérhetetlenné válik, a workflow SHA-ját külön, átnézett PR-ben frissíteni kell. A workflow nem fogad felhasználói ref-bemenetet, mert a job DB-titkot kezel.

## Egyszeri titokbeállítás (a felhasználó végzi, a jelszó nem kerül chatbe)

1. Generálj véletlen jelszót a saját gépeden, pl. `openssl rand -hex 24` (48 karakter; minimum 24, látható ASCII, szóköz nélkül). Mentsd jelszókezelőbe.
2. Privát GitHub repository: **Settings → Secrets and variables → Actions → New repository secret**.
3. Név pontosan: `JG_NEON_PREVIEW_RUNTIME_PASSWORD`; érték: a generált jelszó. A `JG_NEON_PREVIEW_DATABASE_URL` (tulajdonosi URL) már be van állítva.
4. A jelszó nem lehet workflow-bemenet, nem kerülhet commitba, PR-be, chatbe, artefaktumba vagy logba (a GitHub a secretet maszkolja; a workflow sehol nem írja ki).

## Aktiválás és futtatás (jóváhagyás után)

1. Review: a workflow (`.github/workflows/jg-neon-preview-runtime-role.yml`) és ez a dokumentum; a PR **külön jóváhagyással** merge-elendő az alapértelmezett ágba (`feature/jg-os-foundation-v0.1`), mert a `workflow_dispatch` ott érhető el. A v0.6 / v0.6.2 alkalmazáskódot nem kell merge-elni.
2. Actions → *JG OS - Neon preview runtime role* → Run workflow (default ág):
   - **`operation=verify`** (alapértelmezett, csak olvasás): a szerepkör jelenlegi állapotát ellenőrzi. Amíg a szerepkör nincs létrehozva, a várt eredmény: `FAIL jg_runtime szerepkör nem létezik`.
   - **`operation=provision`** + `confirmation=PROVISION JG RUNTIME`: létrehozza (vagy újrafuttatáskor új jelszóra cseréli) a szerepkört, majd lefuttatja ugyanazt az ellenőrzést.
3. Nincs automatikus újrapróbálás; hiba esetén olvasd el a logot (titkok nélkül), ne indíts ismétlést javítás nélkül.

## Vercel automatikus Git-deployment: globális tiltás (`vercel.json`)

A repóhoz GitHub–Vercel integráció kapcsolódik, és a Vercel alapértelmezés szerint **minden olyan ágon** deployol, amelyet a `vercel.json` nem tilt. Egy ág-specifikus tiltás
(`deploymentEnabled: { "<ág>": false }`) ezért nem elég: a PR default ágra történő merge-elése a merge commitot deployolná. Ezért a PR `vercel.json`-ja **globálisan** tiltja az automatikus deploymentet:

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "git": { "deploymentEnabled": false }
}
```

- Ellenőrzött előfeltétel: a default ágon (`feature/jg-os-foundation-v0.1`) jelenleg nincs `vercel.json`, a `package.json` és a `next.config.ts` sem hivatkozik Vercel-konfigurációra, tehát **nincs megőrzendő beállítás**, a fájl kizárólag ezt a tiltást tartalmazza.
- A Vercel a deployolandó commit `vercel.json`-ját olvassa. A merge után a default ág csúcscommitjában már benne van a tiltás, így a merge **nem indít** automatikus deploymentet.
- **Következmény (szándékos):** a merge után a default ágra és minden ágra/PR-re érkező push **semmilyen** automatikus Vercel-deploymentet nem indít, amíg a fájl ilyen. Ez a preview és a production Vercel-oldali indítását is kézi, tudatos lépéssé teszi (pl. dashboard, CLI vagy API).
- **Újraengedélyezés (külön jóváhagyással, átnézett PR-ben):** a `vercel.json` törlése vagy `"deploymentEnabled": true`. Ág-szintű finomhangolás objektum-formával (`"deploymentEnabled": { "<ág>": false }`) lehetséges, de ott a **fel nem sorolt ágak engedélyezettek maradnak**, ezért egyetlen ág kizárólagos engedélyezésére nem alkalmas. A Vercel projektbeállításait (Git-kapcsolat, Deployment Protection, környezeti változók) ez a fájl nem módosítja.
- A v0.6.2 PR (#2) ágán lévő, azonos tartalmú `vercel.json` ettől független; a PR #2-t ez a változtatás nem érinti.
- Korlát: a tiltás hatását a Vercel oldalán közvetlenül nem tudtuk megnézni (az MCP-hozzáférés a projekthez 404/403); a hatás közvetett bizonyítéka a GitHub commit-státuszok hiánya a védett ágakon (a védetlen PR #1 ág deployment-státuszt kapott).

## Beépített kontrollok (workflow)

- Csak `workflow_dispatch`; `if: github.ref == default_branch`; `permissions: contents: read`; közös `concurrency` csoport a migrációs workflow-val (`jg-os-neon-preview-migration`); 15 perces időkorlát.
- Fix célpontellenőrzés a titkos URL-re (host, adatbázis, tulajdonos, `sslmode=require`), `JG_ENV=preview`; a szerepkör neve fix (`jg_runtime`), az `operation` és a megerősítés ellenőrzött.
- A titkok csak azokban a lépésekben érhetők el, amelyeknek kell (a `npm ci` és a Node-beállítás nem látja őket).
- Rögzített commit SHA; nincs felhasználói ref; nincs Trello-import, nincs production-parancs.
- Ellenőrző lépés (csak olvasás, minden tranzakció visszagörgetve): `LOGIN`; nem SUPERUSER/CREATEDB/CREATEROLE/BYPASSRLS; `NOINHERIT`; egyetlen tagság (`jg_app`: SET igen, INHERIT nem, ADMIN nem); nem tulajdonos; nincs CREATE jog; táblajogok **pontosan** a fenti készlet; `users` oszlopjog csak `last_login_at`; RLS-szabály csak a 4 auth/rendszer táblán; a CRM-táblák FORCE RLS-e; majd csatlakozás a futási jelszóval: `SET LOCAL ROLE jg_app` működik, felhasználói azonosító nélkül az RLS 0 sort ad, közvetlen CRM-olvasás/-írás, `CREATE TABLE`, `ALTER TABLE`, jelszó-módosítás, felhasználó-létrehozás, `meta` módosítás tiltott; `meta.environment = preview` olvasható.

## A `verify` működése a `jg_runtime` szerepkör létrehozása előtt (várt, dokumentált viselkedés)

Amíg a szerepkör nincs létrehozva, a `verify` futás **szándékosan hibára fut**:

1. A validálás, a rögzített commit checkoutja, a `npm ci` és a `db status` lépések **sikeresek** (a `db status` a `0001_init` sémát és a `preview` környezetet igazolja).
2. Az utolsó, *Verify runtime role privileges* lépés a tulajdonosi nézetben nem talál `jg_runtime` szerepkört, ezért kiírja: `FAIL jg_runtime szerepkör nem létezik`, és **1-es kilépési kóddal** leáll. A futtatás állapota: **sikertelen (piros)**.
3. A kimenet nem tartalmaz további ellenőrzést: a futási jelszóval való csatlakozás és a jogosultsági vizsgálatok csak létező szerepkörnél futnak. Adat nem íródik, a Neon adatbázis nem változik.

Ez nem hiba, hanem a szerepkör hiányának igazolása. Ezért **nincs értelme előzetes `verify`-t futtatni** pusztán azért, hogy a már igazoltan hiányzó szerepkört újra ellenőrizzük (a Neon MCP-s olvasás szerint a szerepkörlista: `jg_app`, `jg_os_preview_owner`). A `provision` futás ugyanezt az ellenőrzést a létrehozás után hajtja végre, ott a várt eredmény: minden sor `PASS`, a futtatás zöld.

## Ellenőrzés az indítás után, Neon MCP-vel (csak olvasás)

```sql
select rolname, rolcanlogin, rolsuper, rolcreatedb, rolcreaterole, rolbypassrls, rolinherit from pg_roles where rolname in ('jg_app','jg_runtime');
select m.roleid::regrole, m.member::regrole, m.admin_option, m.inherit_option, m.set_option from pg_auth_members m where m.member = 'jg_runtime'::regrole;
select grantee, table_name, privilege_type from information_schema.role_table_grants where grantee = 'jg_runtime' order by 2, 3;
select has_schema_privilege('jg_runtime', 'public', 'CREATE'), has_database_privilege('jg_runtime', current_database(), 'CREATE');
select (select count(*) from customers) c, (select count(*) from tasks) t, (select count(*) from users) u;   -- mind 0 marad
```

## Neon-kompatibilitási lelet (javítva a v0.6.2 PR-ben)

A helyi, Neon-szerű (nem szuperfelhasználó, CREATEROLE/CREATEDB/BYPASSRLS) tulajdonossal végzett próba kimutatta: PostgreSQL 16+ alatt egy ilyen tulajdonos **meglévő** szerepkörön nem adhat meg `NOSUPERUSER/NOCREATEDB/NOBYPASSRLS` opciót az `ALTER ROLE`-ban (a jelenlét számít, nem az érték), ezért a **jelszócsere (újrafuttatás)** `permission denied to alter role` hibával elbukott volna. A szuperfelhasználós tesztek ezt elfedték. Javítás: az ALTER ágon csak a megengedett opciók szerepelnek; a tiltott attribútumokat a kód ellenőrzi, és ha valamelyik be van kapcsolva, a provisioning megáll (nem kerüli meg). Új, Neon-szerű tulajdonossal futó teszt rögzíti (a javítás nélkül elbukik). A Neon konkrét viselkedése csak a tényleges futás után igazolt.

## Következő lépések és nyitott pontok

- A `jg_runtime` létrehozása után a Vercel Preview `DATABASE_URL` a `jg_runtime` felhasználóra cserélendő (direkt host, `?sslmode=require`; a tulajdonosi URL a Vercelbe nem kerülhet). Ez külön jóváhagyás és külön lépés.
- A DB-szintű RLS az alkalmazás által megadott `app.user_id`-re épít (a futási szerepkör bármely aktív felhasználó azonosítóját beállíthatja): az identitást az alkalmazás hitelesíti, az adatbázis nem tudja ellenőrizni. Ez a modell ismert korlátja.
- A `jg_runtime` jelszó forgatása: új secret érték + `operation=provision` újrafuttatás (a régi jelszó azonnal érvénytelen), majd a Vercel változó frissítése.
- A `vercel.json` globális tiltása a merge után minden automatikus Vercel-deploymentet kikapcsol (lásd fent); a preview/production indításához külön jóváhagyott `vercel.json`-módosítás vagy kézi Vercel-művelet kell.
