## 5. Első pilot admin — biztonságos létrehozás (a Neonban jelenleg 0 felhasználó van)

Nincs automatikus felhasználó, nincs alapértelmezett jelszó, nincs seed. A jelszó soha nem kerül chatbe, repóba, workflow-bemenetbe vagy naplóba.

**A) GitHub Actions (ajánlott, a DB-titok nem hagyja el a GitHubot)** — `.github/workflows/jg-neon-preview-admin.yml`:
1. A workflow fájlnak az alapértelmezett ágon is léteznie kell (a `workflow_dispatch` miatt): külön, jóváhagyott PR, mint a #1 (ez a branch a fájlt tartalmazza, de itt még nem futtatható).
2. Repository secret: `JG_PREVIEW_ADMIN_PASSWORD` (generált, ≥16 karakter; a `JG_NEON_PREVIEW_DATABASE_URL` már megvan).
3. Actions → *JG OS - Neon preview pilot admin provisioning* → Run workflow (default ág): `operation=create-user`, `email`, `name`, `confirmation=PROVISION JG PREVIEW USER`.
4. A folyamat ellenőrzi a fix célpontot (host/db/role/TLS), `db status`-t futtat, majd `npm run db -- user:create`. A jelszó csak hash-ként kerül az adatbázisba.
5. Utána a secret törlendő/rotálandó, a jelszó a felhasználó által a `set-password` művelettel cserélhető (a meglévő munkamenetek érvénytelenek lesznek).

**B) Saját gépről:** `JG_ENV=preview DATABASE_URL=… JG_USER_PASSWORD=… npm run db -- user:create <email> "<név>"` (az URL és a jelszó csak a helyi shellben).

Két pilot felhasználóhoz a műveletet kétszer kell futtatni. **Ellenőrzési korlát:** admin nélkül a bejelentkezés Neon ellen nem tesztelhető; a bejelentkezés, a munkamenet és az API-védelem a tesztekben (PGlite és valódi PostgreSQL) igazolt.

## 6. Legkisebb jogosultságú futási szerepkör (javaslat — NEM alkalmazva a Neonon)

**Jelenleg** (ha a `DATABASE_URL` a `jg_os_preview_owner` URL) az alkalmazás a séma-tulajdonos szerepkörrel csatlakozik (CREATEROLE, CREATEDB, BYPASSRLS, `neon_superuser`). A CRM-adatműveletek ugyan `SET LOCAL ROLE jg_app` mellett, RLS-sel futnak, de a kapcsolat jogosultsága a futási folyamatban magas — ezt **nem** nevezzük least-privilege-nek.

**Javaslat:** külön `LOGIN` szerepkör a futáshoz (`src/server/db/runtime-role.ts`, `npm run db -- runtime-role:provision <név>`):
nem tulajdonos, nem szuperfelhasználó, nincs CREATEDB/CREATEROLE/BYPASSRLS, nincs sémamódosító jog; a CRM-adatot csak a `jg_app`-ra váltva (`SET`, nem örökli) éri el; az auth-táblákon minimális jogok
(`users`: SELECT + UPDATE(last_login_at); `sessions`: SELECT/INSERT/UPDATE/DELETE; `login_attempts`: SELECT/INSERT/DELETE; `meta`, `schema_migrations`: SELECT). A migráció és a felhasználókezelés a tulajdonosi URL-lel marad (GitHub Actions / CLI). A jelszó SCRAM-SHA-256 verifierként kerül az adatbázisba (a tiszta jelszó nem jut el a szerverre és az utasításnaplókba).

**Ellenőrzés (helyben, valódi PostgreSQL 18.4, jelszavas hitelesítéssel — `tests/server/runtime-role.test.ts`, 7 teszt):** teljes alkalmazás-folyamat a futási szerepkörrel (belépés, ügyfél, feladat, lezárás, pillanatkép, kijelentkezés, séma-ellenőrzés);
`CREATE/ALTER/DROP/TRUNCATE`, szerepkör-/adatbázis-létrehozás, RLS-kikapcsolás tiltott; a CRM-táblák közvetlenül nem olvashatók, csak `jg_app`-on át, törlés nincs; `users` jelszó-módosítás/létrehozás/törlés, `meta` és `schema_migrations` módosítás tiltott; újrafuttatás idempotens, a régi jelszó azonnal érvénytelen.
**Neon-specifikus működés nincs ellenőrizve** (a Neon konzolos/API-s szerepkörkezeléssel való kölcsönhatás, a `neon_superuser` tagság hatása).

**Végrehajtási terv (jóváhagyás után, Neon preview):**
1. Jóváhagyás: új DB-szerepkör létrehozása a preview adatbázisban (nincs költség; adatot nem érint).
2. Generálj véletlen jelszót (≥24 karakter, pl. `openssl rand -hex 24`); tárold jelszókezelőben.
3. Tulajdonosi kapcsolattal (GitHub Actions workflow bővítése külön, átnézett PR-ben, vagy saját gépről): `JG_ENV=preview DATABASE_URL=<owner URL> JG_RUNTIME_PASSWORD=… npm run db -- runtime-role:provision jg_runtime`.
4. Ellenőrzés Neon MCP-vel (csak olvasás): `pg_roles` (nosuper, nocreaterole, nobypassrls, login), tagság a `jg_app`-ban (`inherit=false, set=true`), jogosultság-lekérdezések.
5. A Vercel Preview `DATABASE_URL`-t a `jg_runtime` URL-re cseréld (direkt host, `?sslmode=require`); a tulajdonosi URL csak a migrációs workflow-ban marad.
6. Visszaállítás, ha gond van: a Vercel `DATABASE_URL` visszacserélése; a szerepkör eltávolítható (`DROP OWNED BY jg_runtime; DROP ROLE jg_runtime;`) — adatot nem érint.

## 7. Bejelentkezés és session a Vercel környezetben (kódszinten ellenőrizve)
