# JG Investment OS v1.2 — Érkezési csatorna az ügyfelekhez

> Állapot: **fejlesztés kész a feature branchen (`claude/elegant-ramanujan-gy7zgv`), élesben NEM fut.** Éles migráció, Preview/Production
> deployment és jogkiosztás csak külön tulajdonosi jóváhagyással történhet (lásd a README-t és a 8. fejezetet).

## 1. Cél

A JG Investment Plus Kft. teljes ügyfélút-mérést épít: weboldal (GA4, Vercel Analytics) → érdeklődés (telefon, e-mail, később webes
visszahívás-kérés) → CRM-ügyfél → tárgyalás → számlanyitás → tőke elhelyezve. Ehhez minden ügyfélnél rögzíteni kell, **melyik csatornán
érkezett**. Ez a mérési rendszer 1. lépése; a következő lépések (9. fejezet) erre épülnek.

Mit ad a v1.2:

| Terület | Működés |
| --- | --- |
| Katalógus | `crm_acquisition_channels`: 12 kezdő csatorna, a Beállítások › Érkezési csatornák oldalon szerkeszthető (`crm.settings.manage`) |
| Új ügyfél | Az érkezési csatorna **kötelező választás**, csak aktív elem; az `Ismeretlen` választható, de nem alapértelmezett. A részlet opcionális (max. 200 karakter) |
| Ügyfél-adatlap | A csatorna és a részlet megjelenik és szerkeszthető; minden módosítás az ügyféltörténetbe kerül (ki, mikor, régi → új) |
| Ügyféllista | Szűrés csatornára; a csatorna oszlop (mobilon a név alatti címke is) |
| Export | Új oszlopok: *Érkezési csatorna*, *Érkezési csatorna részlete*; szűrés csatornára; képletinjekció elleni védelem a meglévő módon |
| Import | Opcionálisan megfeleltethető *Érkezési csatorna* oszlop; hiányzó vagy ismeretlen érték → `Ismeretlen`; az import kapuja és szabályai változatlanok |
| Kimutatás | Pipeline › **Csatornák** (`/pipeline/channels`): csatornánként az ügyfelek száma státuszonként bontva, a létrehozás napja szerinti időszakszűrővel |

## 2. A `source` és az érkezési csatorna különbsége

| | `customers.source` („Adatforrás”) | `customers.acquisition_channel` (+ `acquisition_detail`) |
| --- | --- | --- |
| Mit rögzít | Az **adat eredetét**: honnan jött az adat a CRM-be (pl. import forrása, kontaktadatbázis, GDPR-adatforrás) | **Honnan érkezett az ügyfél**: melyik marketing-/kapcsolati csatornán keresztül találta meg a JG-t |
| Típus | Szabad szöveg | Zárt katalógus (idegen kulcs) + opcionális szabad részlet |
| Példa | „Fiktív rendezvény-névjegyek (2026. okt.)” | `bemutatkozo_level`, részlet: „bemutatkozó levél, 2026. nov.” |
| Import/export | Az import ezt tölti (soronként vagy a varázslóban megadott adatforrás-megnevezéssel); az export a *Adatforrás* oszlopban szerepel | Az import külön, opcionális oszlop; az export külön oszlopok |
| Változás | **Változatlan** a v1.2-ben (viselkedés, import-szabályok, szűrő) | Új |

A két mező egymást nem írja felül; az importnál az `Adatforrás` oszlop és az `Érkezési csatorna` oszlop külön kerül megfeleltetésre.
A felület mindkét helyen magyarázó szöveget ad („az adat eredete – nem azonos az érkezési csatornával”).

## 3. Adatmodell

### 3.1. `crm_acquisition_channels` (0011)

A 0008 konfigurációs katalógusok mintája: `key` (stabil, `^[a-z][a-z0-9_]{1,39}$`), `label` (1–60 karakter, egyedi kis-/nagybetűtől függetlenül),
`description` (opcionális, ≤ 300), `sort_order`, `is_active`, `is_system`, `version`, `created_at/by`, `updated_at/by`, `archived_at`.
Szín nincs (nem státusz).

Kezdő elemek (kulcs → megnevezés, sorrend szerint):

| Kulcs | Megnevezés | Rendszerelem |
| --- | --- | --- |
| `weboldal` | Weboldal (közvetlen kapcsolatfelvétel) | |
| `google_kereses` | Google-keresés | |
| `google_cegprofil` | Google Cégprofil | |
| `facebook` | Facebook | |
| `linkedin` | LinkedIn | |
| `bemutatkozo_level` | Bemutatkozó levél | |
| `ajanlas` | Ajánlás (ügyfél vagy ismerős) | |
| `szemelyes_ismeretseg` | Személyes ismeretség | |
| `kh_ertekpapir` | K&H Értékpapír közvetítése | |
| `rendezveny` | Rendezvény, előadás | |
| `egyeb` | Egyéb | |
| `ismeretlen` | Ismeretlen | **igen** (nem archiválható; a régi és az importált ügyfelek alapértéke) |

### 3.2. `customers` új oszlopai

- `acquisition_channel text NOT NULL DEFAULT 'ismeretlen'` — idegen kulcs a katalógusra (`customers_acquisition_channel_fk`), indexelt.
- `acquisition_detail text NULL` — 1–200 karakter, nincs szélső szóköz, nincs vezérlőkarakter (`customers_acquisition_detail_chk`).

### 3.3. Adatbázis-védelmek (a felülettől és az API-tól függetlenül)

- A katalógus: FORCE RLS; olvasni minden aktív felhasználó, írni csak `crm.settings.manage` joggal. Az alkalmazás-szerepkör (`jg_app`)
  **oszlopszintű** joggal csak a megnevezést, leírást, sorrendet és az aktív állapotot írhatja (új sornál a kulcsot is); törlési joga nincs.
- Őr-trigger (a 0008 közös `crm_catalog_guard()` függvénye): a kulcs és a rendszerjelölés nem változik, a rendszerelem nem archiválható
  (`jg:system_archive`), a verzió, a módosítás ideje és a módosító automatikus.
- Napló-trigger (`crm_catalog_audit()`, bővítve az `acquisition_channel` entitástípussal): minden tényleges változás a `settings_audit`-ba kerül
  ugyanabban a tranzakcióban (régi → új érték). A `settings_audit.entity_type` CHECK bővült.
- Aktív-csatorna trigger az ügyfeleken (`customers_acquisition_active`): új hozzárendelés csak aktív csatornára (`jg:inactive_channel`). Az archivált
  csatornán lévő ügyfél többi adata továbbra is menthető (csak a ténylegesen változó hivatkozást vizsgálja; a 0009 mintája).
- Az `ismeretlen` mindig aktív (`crm_acquisition_channels_system_active_chk`).
- A `customers` tábla jogai nem változtak: a 0001 táblaszintű SELECT/INSERT/UPDATE joga az új oszlopokra is vonatkozik, DELETE továbbra sincs.

## 4. Szabályok a szerveren (nem csak a felületen)

- **Kötelező csatorna kézi felvételnél:** a `newCustomerForm` séma `acquisitionChannel` mezője kötelező (alapérték nincs); a tartományi réteg
  (`DemoRepository.createCustomerFromForm`) ellenőrzi, hogy létezik és aktív. A szerver a `customer.create` műveletben ugyanezt futtatja.
- **Szerkesztés:** a hiányzó mező = változatlan (régi kliens kompatibilis); üres részlet = törlés. Csatornára csak aktív elem váltható; az archivált
  csatornán lévő ügyfél más adata változatlan csatornával menthető. A módosítót a szerver mindig a munkamenetből állítja be.
- **Ügyféltörténet:** `acquisition_change` típusú naplóbejegyzés (`activities`), a meta mezőben a régi/új csatorna-kulcs és részlet; a megjelenítés
  a katalógus aktuális nevét használja. Változatlan mentés nem naplóz. Az `audit_events` bejegyzés csak mezőneveket tartalmaz (érték nélkül).
- **Export:** a csatorna megnevezése a katalógusból; a CSV-cellák a meglévő `neutralizeCsv`-n mennek át (a katalógus-megnevezés és a részlet
  szabad szöveg, ezért is), az XLSX cellái szövegesek. Ismeretlen csatornakulcs a szűrőben 400.
- **Import:** az `Érkezési csatorna` mező opcionális; a feloldás megnevezés vagy kulcs alapján, ékezet- és kisbetű-függetlenül, csak aktív elemre.
  Hiányzó érték csendben `ismeretlen`; felismerhetetlen vagy archivált érték `ismeretlen` + figyelmeztetés (a sor „figyelmeztetéssel” besorolású, a
  meglévő szabály szerint döntést kér). Oszlop nélküli (régi) fájl viselkedése változatlan. A véglegesítési kapu (`JG_CUSTOMER_IMPORT_ENABLED`,
  ellenőrzött adatforrás, nyilatkozat) és az összes többi import-szabály érintetlen. Az importsablon új oszlopot és útmutatósort kapott.

## 5. Jogosultságok

Új jog **nincs**. A csatorna-katalógus szerkesztése a meglévő `crm.settings.manage` joghoz kötött (szerveroldalon frissen ellenőrizve, a
jogosulatlan próbálkozás 403 és naplózott elutasítás). A csatorna kiválasztása, szerkesztése az ügyfélen, a lista szűrése és a Csatornák
kimutatás a napi CRM része (nincs hozzá külön jog). Az export a `crm.customer.export`, az import a `crm.customer.import` joghoz kötött, változatlanul.

## 6. A „Csatornák” kimutatás

`/pipeline/channels` (a Pipeline és az Ügyfelek oldalról is elérhető gombbal). Sorok: minden aktív csatorna (üresen is), az archivált vagy a
katalógusból hiányzó kulcsú csatorna csak ha van ügyfele. Oszlopok: Összesen + a Pipeline-státuszok sorrendben (az archivált státusz csak ha van
benne ügyfél). Az időszakszűrő az ügyfél **létrehozásának napjára** (budapesti nap, mindkét végpont beleértve) vonatkozik. A logikailag eltávolított
ügyfelek nem számítanak. A csatorna neve az ügyféllistára vezet (`/customers?csatorna=<kulcs>`). A számítás tiszta tartományi függvény
(`channelReport`, `src/domain/logic.ts`) — a későbbi „Mérések” oldal ugyanezt használhatja.

## 7. Migráció és rollback

- `0011_crm_acquisition_channels` — additív, egy tranzakció, ellenőrzőösszeggel védett (a meglévő mechanizmus). A meglévő ügyfelek `ismeretlen`
  értéket kapnak (oszlop-alapérték), a `source` és minden más oszlop bájtra azonos marad (teszt). Hiba esetén a teljes migráció visszagördül (teszt).
- **1. szintű (ajánlott) visszagörgetés:** az alkalmazáskód visszaállítása v1.1.x-re. A v1.2 séma visszafelé kompatibilis: a v1.1 kód nem olvassa és nem
  írja az új oszlopokat, az új ügyfelek az alapértéket kapják. Sémaműveletre nincs szükség.
- **2. szintű (séma) visszagörgetés:** `scripts/sql/v1.2-schema-rollback.sql` (egy tranzakció, tulajdonosi kapcsolattal, külön jóváhagyás és friss
  titkosított mentés után). Megszünteti az új oszlopokat, a katalógust és a triggert, visszaállítja a katalógus-napló függvényét és a
  `settings_audit.entity_type` korábbi listáját, törli a 0011 bejegyzést.
  - **Adatvesztés-védelem:** ha bármely ügyfélnél az `ismeretlen`-től eltérő csatorna vagy részlet van, a szkript megáll, és semmi nem változik. Tudatos
    vállalásnál (mentés után): `PGOPTIONS="-c jg.rollback_discard_channels=yes"`.
  - Megmarad: az ügyféltörténet `acquisition_change` bejegyzései (hozzáfűző napló) és a `settings_audit` csatorna-bejegyzései (nem módosítható
    napló; a régi CHECK ezért `NOT VALID`: új sorokra érvényes, a meglévőket nem érinti).
  - A v1.1 sémavisszagörgetés (`v1.1-schema-rollback.sql`) csak **ezután** futtatható (a katalógus-triggerek közös függvényekre épülnek).
- Mentés/visszaállítás: az új katalógustábla a logikai mentés része (`BACKUP_TABLES`, `CATALOG_TABLES`); a régebbi (0009/0010) mentések a v1.2 sémába
  változtatás nélkül visszaállíthatók (az ügyfelek `ismeretlen`, a katalógus a kiinduló 12 elem). Tesztelt.

## 8. Ellenőrzés és tesztek

Parancsok: `npm run typecheck`, `npm run lint`, `npm test` (a migrációs tesztekkel, PGlite), `npm run build`, e2e: `npm run e2e` (v0.6 + v1.0), `node e2e/v1.1-settings.e2e.cjs`,
`node e2e/google-login.e2e.cjs`, **új:** `npm run e2e:channels` (`e2e/v1.2-channels.e2e.cjs`; 390 és 1440 px, axe WCAG A/AA, képernyőképek).

Új tesztek:

- `tests/acquisition-channels.test.ts` (tartomány): kezdő katalógus; kötelező csatorna, aktív-elem szabály, részlet-korlátok; a `source` függetlensége;
  ügyféltörténet (régi → új, módosító, nem naplózó mentés); szűrés; kimutatás-számok és időszakszűrés (Budapest-határ); import-feloldás.
- `tests/server/acquisition-channels.test.ts` (DB + API, valódi PostgreSQL): migráció (meglévő ügyfelek `ismeretlen`, bájtra azonos adat, ismételt futtatás,
  hiba esetén teljes visszagörgetés), rollback (adatvesztés-védelem, tudatos vállalás, újra előre); katalógus-védelmek (kulcs/rendszerjelölés nem írható,
  rendszerelem nem archiválható API-n és DB-n, jog nélkül nem írható, törlés nincs, napló); kötelező csatorna kézi felvételnél; ügyféltörténet-bejegyzés
  és idempotencia; archivált csatorna kezelése (API, DB, upsert); kimutatás az adatbázis számaival; export (oszlopok, szűrés, képletvédelem CSV/XLSX);
  import (oszlop, figyelmeztetés, kapu változatlan, sablon); mentés/visszaállítás (új és régi formátum).
- Módosított meglévő tesztek: a kézi ügyfélfelvételt végző tesztek megadják a (mostantól kötelező) csatornát; a migrációs tesztek az új oszlopokat is
  figyelembe veszik; a v1.1 sémavisszagörgetési teszt előbb a v1.2 szkriptet futtatja; az RLS-teszt az aktív-csatorna őr hibaüzenetét is elfogadja.

Képernyőképek: `docs/screenshots/v1.2/` (mobil 390 px és desktop 1440 px: új ügyfél, adatlap szerkesztés és előzmények, ügyféllista szűrővel, Csatornák kimutatás, beállítások).

## 9. Következő lépések (NEM részei a v1.2-nek; az adatmodell felkészített rájuk)

1. **Webes visszahívás-kérő űrlap → CRM:** a weboldali űrlapból érkező kérés ügyfelet hoz létre `acquisition_channel = 'weboldal'` (vagy a megfelelő
   csatorna) értékkel; az `acquisition_detail` hordozhatja az oldal/kampány azonosítóját (pl. „TBSZ-útmutató”). A `customer.create` művelet ehhez
   már a kötelező csatornával fut; külön, jogosultsággal és sebességkorláttal védett nyilvános végpont kell.
2. **E-mail-rendszer → CRM:** a bemutatkozó levél küldése az ügyféladatlapról; a küldés eredménye `bemutatkozo_level` csatornaként és
   `acquisition_detail`-ként („bemutatkozó levél, 2026. nov.”) is rögzíthető, a változás az ügyféltörténetben már most követhető.
3. **„Mérések” oldal:** a GA4- és Search Console-adatok összekötése a `channelReport` számaival (látogatás → érdeklődés → ügyfél → számlanyitás →
   tőke elhelyezve csatornánként). A kimutatás időszakszűrője és a státuszonkénti bontás erre készült.

## 10. Tulajdonosi döntésre vár

- Az `Ismeretlen` csatorna és a kezdő elemek megnevezéseinek jóváhagyása (a Beállításokban később is módosíthatók, a kulcsok nem).
- Az alkalmazás verziócímkéje (jelenleg „v1.1” a fejlécben) — kiadási döntés.
