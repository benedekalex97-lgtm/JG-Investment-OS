# v0.6 — Tartós adattárolás, hitelesítés, jogosultság (architektúra-döntés és üzemeltetés)

> **Állapot: "Implementáció elkészült, tartós infrastruktúra összekötésre vár."**
> A kód, a séma, a hitelesítés és a jogosultság helyben és egy valódi, külön PostgreSQL szerveren tesztelt. **Nincs jóváhagyott külső
> adatbázis-szolgáltató**, ezért előnézeti/éles környezet még nincs összekötve; éles használatra a rendszer **nem kész** (lásd „Blokkolók").
> A rendszer adatbázis nélkül *nem* esik vissza böngészőtárolásra vagy memóriára: „Tartós infrastruktúra összekötésre vár” állapotot mutat.

## 1. Architektúra-audit (v0.5.1 kiindulás)

| Terület | v0.5.1 | Következmény |
|---|---|---|
| Adattár | `DemoRepository` (memória) + `sessionStorage` a böngészőben | fül bezárásakor elveszik; nincs szerveroldali mentés |
| Írási útvonal | szinkron repository-hívások a komponensekből | az adatbázis aszinkron → 10 hívási pont átírva |
| Hitelesítés | nincs; két fiktív „demófelhasználó” | valódi bejelentkezés kell |
| Jogosultság | nincs | szerveroldali ellenőrzés + adatbázis-szintű RLS |
| Üzleti szabályok | tiszta tartományi réteg (`src/domain`, `DemoRepository`) | **újrahasznosítva** a szerveren (nincs másolt szabály) |

## 2. Technológiai döntés

**PostgreSQL + alkalmazás-szintű hitelesítés + szerveroldali jogosultság + verziózott migrációk.** A `pg` meghajtó bármely
PostgreSQL-lel működik (`DATABASE_URL`), ezért a szolgáltató **nem kötött** (Supabase Postgres, Neon, Vercel-kompatibilis felügyelt
Postgres, saját szerver). Indoklás: (1) a kód nem függ szolgáltatói SDK-tól, így szolgáltatóváltás költsége alacsony; (2) a jogosultság
az adatbázisban (RLS, szerepkör) él, nem csak az alkalmazásban; (3) a kliens soha nem kap adatbázis-kulcsot; (4) a Supabase Auth/Data API
nem szükséges, ezért nincs véletlenül kitett publikus API (a hitelesítést és az adat-hozzáférést a saját, szerveroldali API végzi).

* **Helyi fejlesztés / teszt / E2E:** PGlite (valódi PostgreSQL WASM-ban, fájl alapú, tartós) — csak `JG_ENV=local` és Vercelen kívül; élesben tiltott.
* **Előnézet / éles:** `pg` + `DATABASE_URL` (külső, kezelt PostgreSQL).
* A tesztek PGlite-on **és** egy valódi, külön folyamatban futó PostgreSQL 18.4 szerveren is lefutottak (`JG_TEST_DATABASE_URL`).

Nem jött létre és nem lett összekötve semmilyen külső erőforrás. A fiókban látható Supabase projektek (`Axflow-OS`, `axflow-pricing-test`)
**más termékhez** tartoznak, és ehhez a projekthez nem lettek használva vagy módosítva.

## 3. Adatmodell (migráció: `src/server/db/migrations/0001_init.ts`)

`customers` (típus, név, kapcsolati státusz, kapcsolatok, forrás, időbélyegek) · `company_contacts` · `tasks` (ügyfél, létrehozáskori státusz,
típus, **Input kulcs** + opcionális megjegyzés, régi szabad szöveges leírás, határidő, állapot) · `task_results` (**Output kulcs** +
opcionális megjegyzés, lezárás ideje, lezáró felhasználó; hozzáfűző, újranyitás után is megmarad) · `audit_events` (hozzáfűző: ki, mikor, mit)
· `users`, `sessions`, `login_attempts`, `request_log` (idempotencia), `meta` · megőrzött régi adat: `processes`, `contactability`,
`customer_restrictions`, `activities`.

* Idegen kulcsok és CHECK-ek az adatbázisban (hét státusz, feladat-állapot, ügyféltípus-névszabály, egyedi elsődleges kapcsolattartó).
* Az **Input/Output opciókat az adatbázis nem köti kényszerrel** — a lista (`src/domain/constants.ts`: `TASK_INPUT_OPTIONS`, `TASK_OUTPUT_OPTIONS`) bővíthető migráció nélkül; a tárolt kulcs stabil, a címke szabadon átírható; kivezetett kulcs a kulcsként jelenik meg (nincs adatvesztés).
* Régi (v0.5 előtti) szabad szöveges Input/Output: változatlanul megmarad (`description`, `task_results.output_text` kulcs nélkül), nincs kitalált leképezés.

## 4. Hitelesítés és jogosultság

* Belépés e-mail + jelszó; scrypt hash (egyedi só), min. 12 karakter; ismeretlen e-mail ugyanazt a választ adja; zárolás: 5 sikertelen/15 perc fiókonként, 30/IP.
* Munkamenet: véletlen token, az adatbázisban csak SHA-256 hash; `HttpOnly`, `SameSite=Lax`, HTTPS-en `__Host-` előtag + `Secure`; 8 óra tétlenségi / 7 nap abszolút lejárat; kijelentkezés, letiltás és jelszócsere azonnal érvényteleníti.
* CSRF: módosító kérés csak azonos eredetről (Origin/Sec-Fetch-Site) és JSON tartalommal.
* Minden CRM-végpont hitelesítést igényel; a rögzítő/felelős **mindig a munkamenetből** jön (a kliens által küldött érték elutasítva).
* Két pilot felhasználó, közös ügyfélnézet; alkalmazásszintű admin ≠ infrastruktúra/DB-admin (a jelszavakat a `db` CLI-vel lehet kezelni, nincs jelszó a repóban).
* **Adatbázis-szintű védelem (RLS):** a CRM-táblákat a korlátozott `jg_app` szerepkör (nem tulajdonos, nem szuperfelhasználó, `NOBYPASSRLS`) érheti el, és csak ha a tranzakcióban az `app.user_id` **aktív** felhasználó. Törlési jog sehol nincs; a naplók (aktivitás, eredmények, audit) csak hozzáfűzhetők; a tiltakozás/korlátozás táblája csak olvasható; a hitelesítési táblákhoz a `jg_app`-nak nincs joga. Ezt a `tests/server/rls.test.ts` ellenőrzi (PGlite + valódi PG).
* Nincs titkos DB-kulcs a böngészőben; a hibaválaszok általánosak (nincs DB-részlet, személyes adat); a napló csak hibakódot tartalmaz.
* Biztonsági fejlécek: nosniff, X-Frame-Options DENY, Referrer-Policy, Permissions-Policy. (CSP nincs — külön feladat.)

## 5. Írási folyamat (adatvesztés elleni védelem)

Egy művelet = egy tranzakció: idempotencia-zár → ügyfélsor zárolása (`FOR UPDATE`) → szelet betöltése → **a közös tartományi szabályok** (`DemoRepository`) →
különbség mentése (**csak beszúrás/frissítés; törlés az invariáns miatt hibát dob**; korábbi eredmények/tiltakozás nem módosítható) → audit → `request_log`.
Hiba esetén teljes visszagörgetés (tesztelve). Azonos `requestId` ugyanazt az eredményt adja (nincs duplikátum; párhuzamos kéréseknél is). A kliens a bizonytalan
kimenetelű (hálózati/5xx) kérést ugyanazzal az azonosítóval próbálja újra. A felület minden sikertelen mentésnél egyértelmű üzenetet ad, az űrlap nyitva marad.

## 6. Migrációk

* Verziózott, időrendi, tranzakciónként futó, ellenőrzőösszeggel védett (alkalmazott migráció nem módosítható); `npm run db -- migrate`.
* **Additív alapértelmezés:** a destruktív utasítás (`drop`, `truncate`, `delete from`, oszlop-típusmódosítás, RLS kikapcsolás) jóváhagyás-jelölés (`-- allow-destructive: <indok>`) **és** futtatáskor `JG_ALLOW_DESTRUCTIVE_MIGRATION=<id>` nélkül nem fut (tesztelve).
* **Az alkalmazás nem migrál és nem seedel:** előnézeten/élesben a migráció kézi lépés; helyben (PGlite) automatikus. Új verzió telepítése nem töröl és nem inicializál adatot (tesztelve: újraindítás/újra-migráció után az adat megvan).
* A `meta.environment` a migrációkor rögzül; eltérő `JG_ENV` esetén az alkalmazás nem szolgál ki adatot (`environment_mismatch`).

## 7. Környezetek szétválasztása

| Környezet | `JG_ENV` | Adatbázis | Adat |
|---|---|---|---|
| Helyi | `local` | PGlite könyvtár vagy helyi PG | fiktív |
| Előnézet / staging | `preview` | **külön** DB (`DATABASE_URL`, csak Preview scope-ban) | fiktív vagy külön jóváhagyott |
| Éles | `production` | **külön** DB (csak Production scope-ban) | valós, csak külön jóváhagyás után |

Védelmek: Vercel `VERCEL_ENV` ≠ `JG_ENV` → `environment_mismatch`; `JG_PRODUCTION_DB_HOSTS` listán szereplő hosztra nem éles környezet nem csatlakozhat; a DB-ben tárolt környezet-címke; `JG_PGLITE_DIR` élesben/Vercelen tiltott. Éles adat nem másolható tesztadatbázisba.

## 8. Mentés és helyreállítás

* **Logikai mentés:** `JG_ENV=… DATABASE_URL=… npm run db -- backup <új-fájl>` (nem ír felül meglévő fájlt, 0600 jogosultság). A fájl **személyes adatot és jelszó-hash-eket** tartalmaz: titkosítva, hozzáférés-védett helyen tárold, ne kerüljön verziókezelésbe.
* **Visszaállítás:** friss, **üres** és migrált adatbázisba: `npm run db -- migrate && npm run db -- restore <fájl>` (nem üres DB-re, más környezetre vagy eltérő sémaverzióra megáll; egy tranzakció; sorszám-ellenőrzés). Éles célnál `JG_CONFIRM_PRODUCTION=yes` kell.
* **Tesztelt visszaállítás (fiktív adat):** `tests/server/backup.test.ts` — forrás → mentés → külön céladatbázis → tartalom azonos, belépés és CRM működik; PGlite és valódi PG-n is.
* Szolgáltatói szinten (kezelt PG): napi automatikus mentés / PITR a csomagtól függ (lásd 11.), a **visszaállítási próbát a kiválasztott szolgáltatónál külön el kell végezni** üzembe helyezés előtt. Az ütemezett mentés beállítása még **nincs** kész.

## 9. Régi böngészős adat (sessionStorage)

Nincs automatikus import és nincs automatikus törlés. A felület felismeri (v0.1/v0.2–v0.5.x kulcsok), jelzi, JSON-ba exportálhatóvá teszi, a törlés külön megerősített döntés. Adatbázisba csak **külön, jóváhagyott, ellenőrzött művelettel** kerülhet (nincs implementálva; a fiktív/ismeretlen/valós adat nem keverhető, bizonytalan státusz nem képezhető le).

## 10. Beállítási útmutató (amikor a szolgáltató jóváhagyott)

1. Hozz létre **két külön** PostgreSQL adatbázist (preview, production), régióban az uniós adatkezelési követelmények szerint. *(Ez a lépés felhasználói jóváhagyást és esetleg költséget igényel — a kód nem hozza létre.)*
2. Vercel → Project → Settings → Environment Variables: `JG_ENV=preview` + `DATABASE_URL=<preview URL>` csak **Preview** scope-ban; `JG_ENV=production` + `DATABASE_URL=<prod URL>` csak **Production** scope-ban; opcionálisan `JG_PRODUCTION_DB_HOSTS=<prod hoszt>`. A `DATABASE_URL` `?sslmode=require`-t tartalmazzon.
3. Migráció (kézzel, a megfelelő környezeti változókkal): `npm run db -- migrate` (előbb preview). A migrációs kapcsolatnak jogosultnak kell lennie szerepkör létrehozására (`jg_app`).
4. Pilot felhasználók: `JG_USER_PASSWORD=… npm run db -- user:create <email> "<név>"` (kétszer).
5. Ellenőrzés: `npm run db -- status`; bejelentkezés; mentési/visszaállítási próba.
6. Éles üzem csak a „Blokkolók” feloldása és külön jóváhagyás után.

* Vercel Pro: **20 USD/hó** (a Hobby csomag csak személyes, nem kereskedelmi célra). Forrás: <https://vercel.com/pricing>, <https://vercel.com/docs/plans/hobby>.
* Két külön adatbázis (preview + production) esetén a költség szolgáltatótól függően nő. A választott szolgáltató végleges ára **nincs jóváhagyva**.

## 12. Ismert korlátok és kockázatok

* A teljes snapshot minden frissítéskor betöltődik (2 pilot felhasználó, kis adatmennyiség); nagyobb adatmennyiségnél lapozás/részleges lekérés kell.
* A közös nézet 30 másodpercenként és fókuszra frissül (nincs valós idejű push); egyidejű szerkesztésnél az utolsó mentés érvényes (ügyfélsor-zár védi a rekord-konzisztenciát).
* Az `audit_events`/`request_log` megőrzési ideje nincs szabályozva.
* A PGlite nem többfolyamatos: egy könyvtárat egyszerre egy folyamat nyithat meg (csak helyi használatra).
* A bejelentkezési zárolás IP-je az `x-forwarded-for` fejlécből jön (Vercelen megbízható).
* Szolgáltatói mentés/PITR beállítása és visszaállítási próbája a szolgáltatóval hátra van.
